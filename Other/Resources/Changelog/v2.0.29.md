# Release notes

## Changes

- **Breaking:** Removed the public static field `APIServer.Services.Database.GenericDatabaseInteractor.Lock`. It was a lock-object which was shared by all interactor-instances of the process and which applications could (and did) replace at runtime, which silently voided the mutual exclusion for everybody who was already using the old object. Applications which assigned that field have to remove the assignment; the interactor protects its connection on its own now.
- `APIServer.Services.Database.GenericDatabaseInteractor` protects its database-connection for the entire duration of its usage now (via the new `Misc.ExclusiveAccess`), not only while the connection is handed out. There is exactly one connection per interactor, so a caller which needs the database waits until the current user is finished with it. Before this, the background-thread which re-establishes the connection was able to dispose and replace a connection while another thread was still working with it, which turned an ordinary connection-loss into an `ObjectDisposedException` that masked the actual error. The new methods `UseConnection(Action<DbConnection>)` and `UseConnection<T>(Func<DbConnection, T>)` are the supported way to work with the connection; `GetConnection` is only valid inside such an access now. `DBUtilities.RunTransaction` holds the access for the complete transaction.
- `APIServer.Services.Database.GenericDatabaseInteractor` forgets the exception of a failed connection-attempt once it is connected again, and `IsAvailable` does not report that exception anymore while the database is available. Before this, the exception of the very first failed attempt (typically `57P03: the database system is starting up`, because the database-container is usually still booting while the application already runs) was kept forever and was attached as the inner exception to every later error-report of the interactor, which pointed the reader at a situation which was long over.
- Fixed `APIServer.Services.Database.GenericDatabaseInteractor.Dispose` holding a lock while waiting for the connection-thread to end. The connection-thread needs the same lock to finish its iteration, so disposing could deadlock until the wait ran into its timeout.
- Added `Misc.ExclusiveAccess`. It grants exclusive access to a resource for the entire duration of an operation: whoever needs the resource waits until the current user is finished with it. In contrast to a plain `SemaphoreSlim` it is re-entrant for the owning thread, so an operation on the protected resource can call another operation on the same resource without deadlocking itself. In contrast to a `lock`-statement the protected resource can be replaced while it is protected, because the access is bound to the `ExclusiveAccess`-object and not to the resource-instance.
