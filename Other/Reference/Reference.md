# GRYLibrary

## Features

GRYLibrary is a general-purpose utility-library and framework (for example a WebAPI-server-framework, cryptography-primitives and various helper-types) rather than a product with a small set of discrete user-facing features. The features it exposes are its public api-surface and are documented at the api-level; no separate feature-table is maintained here.

## Findings

This table collects the known findings of this repository from code-reviews, security-analyses, bug-lists and lists of open issues.
Every finding has an id of the form `<prefix>-<n>`. The prefix states the category of the finding: `SEC` for security-relevant findings, `BUS` for incorrectly implemented business-logic, `PER` for findings with a performance-impact, `BUG` for any other bug and `OTH` for everything else. The numbers are assigned ascending per prefix starting at 1, without leading zeros. Ids are never reused: when a finding is removed its id is retired rather than handed to another finding. Only fixed findings have their id struck through. The former id of each finding (from the previous `GRY`/`F`/`OI`/`HNT`-scheme) is recorded in its `Notes`-cell.
The state of every finding was verified against the source-code on 2026-10-08.
The findings `SEC-36` to `SEC-48`, `PER-4`, `PER-5` (former ids `GRY-41` to `GRY-55`) were added by a follow-up OWASP-Top-10:2025-analysis of the WebAPI-server-framework on 2026-10-22 and verified against the source-code of version 2.1.9.

### OWASP-Top-10-analysis

The findings with the prefix `SEC` (former prefix `GRY`) are the result of a security-analysis of this library against the [OWASP Top 10:2025](https://owasp.org/Top10/2025/).
The analysed version was 2.1.3.
The analysis is a review of the source-code; it is not a penetration-test.
The findings are stated from the point of view of a consumer: this library is not an application but the framework which its consumers build their api-server on, so a weak default here becomes a weakness in every product which uses it, and a security-control which the library does not offer is a control which no consumer has.

The analysis concentrates on the parts which an api-server-consumer really runs, because those are the ones with an attack-surface:

| Area                             | Files                                                                                                                                                 | Relevance                                                                    |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Pipeline-composition and hosting | `APIServer/APIServer.cs`, `APIServer/Settings/Configuration/ServerConfiguration.cs`                                                                   | decides which middleware runs in which order, and configures kestrel and tls |
| Authentication                   | `APIServer/MidT/Auth/AuthenticationMiddleware.cs`, `APIServer/Mid/AuthS/*`                                                                            | decides for every request whether it is authenticated                        |
| Authorization                    | `APIServer/MidT/Aut/AuthorizationMiddleware.cs`, `APIServer/Mid/AutS/*`                                                                               | decides whether the caller may perform the operation                         |
| Credential-transport             | `APIServer/Services/CredH/*`                                                                                                                          | extracts the access-token from the request                                   |
| Authentication-services          | `APIServer/Services/Trans/TransientAuthenticationService.cs`, `APIServer/CommonDBTypes/User.cs`, `APIServer/CommonAuthenticationTypes/AccessToken.cs` | the reference-implementation of login, password-handling and token-handling  |

### Positive observations

The analyses recorded the following as already sound and worth keeping:

- The authorization-code-flow with pkce and S256, and the state- and verifier-generation from `RandomNumberGenerator`.
- The full validation of issuer, signature and lifetime of a jwt against the discovery-document.
- The parameterized data-access-layer: a command is built from a sql-text plus real `DbParameter`-objects, and the queries which the library executes itself against `information_schema` are constant texts with bound parameters.
- The default exception-handler (`GetExceptionResponceContent`) returns an empty body, so no stack-trace and no exception-message reaches the client.
- Request-headers are logged only when a consumer lists them explicitly in `LoggedHTTPRequeustHeader`, which is empty by default.
- The secure default of `TrustForwardedHeader` (`false`).
- Kestrel is configured with `AddServerHeader = false`.
- The authentication-cookie is issued with `HttpOnly`, `Secure` and `SameSite=Strict` (`CookieTools.GetCookieWithSpecificExpiredDate`).
- `app.UseRouting()` runs before the authentication- and authorization-middlewares, so the attribute-based checks see the resolved endpoint.
- The thread-safe resource-loader reads only embedded resources.
- Every nuget-dependency is pinned to an exact version and the project keeps a lock-file.

### Prioritized remediation plan

1. Replace the password-handling: a real key-derivation-function with a salt, offered as a service of the library, and remove or implement the argon2-stub (~~SEC-10~~, ~~SEC-11~~, ~~SEC-50~~).
2. Make the oidc-validation strict: require the audience, require https for the authority, and carry the issuer in the principal (~~SEC-20~~, SEC-13, SEC-21).
3. Stop logging bodies unredacted, and exclude the authentication-routes by default (SEC-27, SEC-28, SEC-49).
4. Make the access-control fail closed: authentication required by default, anchored allowlist-patterns, authorization from the established principal, and no silent disabling through an empty group-set (SEC-1, SEC-2, SEC-3, SEC-4, SEC-54).
5. Deliver the threat-protection the library already outlines: a concrete rate-limiting-middleware with a pipeline-hook, plus a failed-login-counter and a lockout (SEC-15, SEC-33, SEC-52).
6. Remove the synchronous-over-asynchronous pipeline and the `AllowSynchronousIO`-flag (PER-2, PER-1, PER-6).
7. Fix the oidc-bearer-path and the credential-header-contract, and cache the discovery-document and the key-set (SEC-22, SEC-23, PER-3).
8. Let the consumer protect the maintenance-routes, and offer a security-header-middleware (SEC-5, SEC-6).
9. Make the remaining robustness-findings behave correctly (SEC-31, BUG-1, SEC-32, BUG-2), decide what happens with the mfa-stub and the deactivation-flag (SEC-16, SEC-17), and work off the integrity- and supply-chain-findings (SEC-25, SEC-26, ~~SEC-8~~, ~~SEC-9~~, SEC-12, ~~SEC-14~~, SEC-18, ~~SEC-19~~, SEC-24, SEC-29, ~~SEC-30~~, SEC-34).
10. Add tests for every security-relevant path (SEC-35).
